# 設計判断の記録（ADR）

{{project}} の大きな判断を、1 ファイルに 1 つの決定で記録する。

## 決まりごと

- ファイル名は `YYYYMMDD-<slug>.md`。日付は決めた日、slug は題名を英語のケバブケースにしたもの。番号も索引も付けない（並行した変更でぶつかるため）。
- 各記録は状態と、「背景」「決定」「検討した他の案」「結果」の節を持つ。
- 採用した記録は書き換えない。決定が変わったら新しい記録で置き換え、両方の状態にそう書く。
- 記録どうしはファイル名で参照する。仕様へはリンクしない。仕様は変わり続けるので、決定は記録の中で完結させる。

## 記録に書くもの

1 つの記録には 1 つの決定だけを書く。作業中に決めたことを全部書く場所ではない。

各行について、次を問う。

> これを変えるとき、この記録を置き換える新しい記録が要るか。

- 要る: 決定の一部。書く。
- 要らない（コードや仕様を直す普通の変更で済む）: 仕様か実装。書かない。

形式・置き場所・文字コード・画面の細部・手順の順番は、ほぼ必ず「要らない」になる。

## 書く順番

この順に書く。途中で細部を書くかどうかを 1 行ずつ迷わない。

1. 題名: 決定を一文で書く。この一文が決定。
2. 決定: 題名を言い直す。上の問いを通ったことだけを添える。
3. 検討した他の案: 題名の決定の代わりになり得た案だけを、採らなかった理由とともに書く。
4. 結果: その決定から直接出ることだけを書く。
5. 背景: なぜ題名が答えになったかを読み手が分かるのに要ることだけを書く。

レビューで直すことになったら、前の版を見ずに、題名から書き直す。前の版に手を入れると、新しい決定には要らない細部が残る。

コミットの前に、もう一度すべての行に上の問いを当てる。

## 例

この粒度で書く。

```markdown
# 利用者が登録した語は、別の辞書に持つ

状態：採用

## 背景

利用者が登録した語を、同梱の辞書に追記していた。更新のたびに同梱の辞書を置き換えるので、登録した語が消えていた。

## 決定

利用者が登録した語は、更新が触れない別の辞書に持つ。

## 検討した他の案

- 更新のあとに、登録した語を同梱の辞書へ書き戻す。書き戻しに失敗すると語が消え、どれが利用者の語か見分けられなくなる。

## 結果

- 更新は同梱の辞書をまるごと置き換えてよい。
- 引くときは 2 つの辞書を見る。
```
