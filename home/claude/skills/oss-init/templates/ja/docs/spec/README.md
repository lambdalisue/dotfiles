# 仕様

{{project}} が使う人に約束することを、話題ごとに 1 ファイルで書く。

## 誰が読むか

{{project}} を使う人と、{{project}} と連携するほかのプログラムの作者。仕様には、その人たちが頼りにできることを書く。コードについて正しいことを何でも書く場所ではない。

## 仕様に書くもの

層ごとに持つものは一つ。

| 層 | 持つもの |
| --- | --- |
| ADR | 一つの決定とその理由 |
| 仕様 | 利用者や、連携するほかの部品が頼りにできる振る舞い |
| テスト | 振る舞いを決める細部（規則・境界・対応表） |
| コード | やり方 |

細部はテストが持つので、仕様はテストより狭い。仕様に残るのは、テストでは言い表しにくいもの。たとえば、利用者がたどる流れ、「すでにあるデータは書き換えない」といった約束、何を扱うかの範囲。

各行について、次の二つを問う。

1. この行はテストで押さえられるか（押さえるべきか）。そうなら、テストに書き、仕様には書かない。
2. これを変える変更は、利用者から見て振る舞いが変わったと言われるか。言われないなら、仕様ではない。

次のものはたいてい問いを通らない。仕様に出てきたら外す。

- 番号付きの手順（アルゴリズム）
- 対応表
- ほかのプログラムのファイルの場所
- 正確な文字列（ヘッダ、ファイル名）
- 並び順の規則、画面の配置

### 例外: {{project}} が定める形式

{{project}} が定めていて、ほかの人が書く形式（{{project}} のデータファイルや設定ファイル）は、外の作者が読むので、仕様に細部まで書く。ほかの人が定めた形式（ほかのプログラムのファイル）は {{project}} が約束するものではないので、読み方はコードとテストに任せる。

## 書く順番

1. 何を約束するかを、先に短く書く。細部は書かない。
2. 細部はテストの名前として書く。テスト名を文にしておけば、テストの一覧がそのまま読める仕様になる。
3. レビューの指摘で直すときは、利用者から見える振る舞いが変わらない限り、仕様に触れない。

コミットの前に、もう一度すべての行に二つの問いを当てる。

仕様は、振る舞いを変える変更の中でその場で書き換える。「あとで更新する」とは書かない。なぜそうするかも書かない。理由は ADR（`docs/adr/`）が持つ。
